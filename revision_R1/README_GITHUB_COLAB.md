The single stable production notebook is `My Drive/ReVision/Revision_R1_Production_Colab.ipynb`. It is generated from the latest saved Drive notebook after removing temporary recovery-only cells, and pins exactly one full commit SHA in Cell A. It never fetches a branch head automatically or downloads runner code per matrix run.

## Exact execution order

Run Cells A → B → C → D. Cell A pins code and verifies the canonical storage session. Cell B verifies the Drive preflight/effective schedule and uses only the existing Drive NPZs or checksum-verified local caches; external dataset downloads are disabled. Cell C validates the frozen plan, reads the canonical completion registry, confirms Run 1 is already finalized and registered, reuses its existing storage measurement without recomputing it, checks only the next pending run's incremental capacity plus reserve, and records an immutable selected-commit/protocol binding. The full-matrix projection is informational. Cell D is read-only and reports lease/progress/checkpoint state.

Cell E is a deliberate no-op for Run 1: it does not load a model, train, measure storage, register completion, or rerun finalization. Cell F is the remaining-matrix continuation; its launch switch defaults to `False`. If explicitly enabled after review, it preserves the single-worker lease, skips identity-validated completions, and resumes interrupted runs only from compatible verified checkpoints. Changing compute account does not change Drive paths or run/checkpoint identities. A live lease is never bypassed because the runtime account changed. Cell G exports lightweight results; checkpoint backup is off by default.

## Proven checkpoint workflow reused

The first-paper V15.5 Standard-A Colab builder (`runners/v15_5_standard_a/tools/build_colab_notebook.py`) mounted Drive once, pointed the launcher at a fixed output root, and reran the same registry-backed launcher. Its launcher (`launch_v15_5_standard_a.py`) skipped completed rows and marked interrupted/failed attempts; `v15_5_runner/checkpointing.py` wrote a temporary checkpoint then atomically replaced `checkpoint/latest.pt`. `v15_5_runner/training.py` saved after each task and restored the saved `next_task` cursor and RNG before continuing. Revision_R1 reuses those operational ideas—one predictable run namespace, atomic task-boundary recovery, and same-run resume—but retains its own checkpoint format and explicit OAuth API/local-staging backend because the Drive mount can belong to a different account. It does not restore from V15.5 checkpoint files.

## Frozen identities and checkpoint behavior

The compatible training-core identity remains `1731ee525e3297e276609040295977e4c02f5aeab8e4ab125dd08fbcb993dc9c`. The frozen effective schedule remains `7d327c9ce84a096201d06f910f88d022f4e056ad32e090a84e19be393747d212`. The selected Git commit is recorded separately and is not added to training identity unless a verified training-core or protocol change requires a different checkpoint identity. Existing paths, configurations, run IDs, optimizer/RNG/sampler state, exact cursor, and checkpoint discovery remain unchanged.

Dataset bytes are read from the configured canonical Drive source. If an archive is absent, only a complete checksum-verified local cache matching the passed preflight is accepted. No external dataset download or automatic dataset migration is performed.

Training and serialization stay on local Colab disk. Local recovery is due approximately every five monotonic minutes; Drive recovery publication is due approximately every fifteen minutes, plus task boundaries and graceful interruption. The timers are completion-based. Drive publishes only the newly due generation, reads it back through the same canonical Drive API identity, checks exact parent/name/owner/quota/size/MD5 and checkpoint integrity, then permits recovery pruning. Two verified recovery generations are retained when the account owns them. The eleven task-boundary artifacts are separate and are not pruned.

Mixed-owner historical files are preserved even if the current account has `canDelete`; no automatic transfer, rewrite, or deletion is performed on them. Such protected legacy generations can temporarily make physical recovery retention exceed two. New artifacts must be owned and quota-charged by the canonical account. Write/read-back failures keep the last verified recovery point intact. API errors retry only when transient; identity, permission, quota, and ambiguous-file errors stop immediately.

Capacity is checked through the canonical storage API account—not the compute account—and each next pending run is gated on its incremental peak plus the unchanged reserve. Local staging free space is checked separately before downloads and writes. The 100-run projection is displayed as planning information only; it does not require capacity for all future runs before beginning one. Capacity is rechecked before each large checkpoint publication. Unknown quota is never converted to an invented free-space number. Cell A probes Drive v2 ETag conditional updates on an exact temporary file through the same OAuth owner; it verifies first-write bytes, distinct next ETag, stale `If-Match` HTTP 412, unchanged bytes after stale attempt, and cleanup. If any check fails, worker launch remains blocked.

## Runtime and routine updates

Cell A expects the observed Colab image: Python 3.12.13, NumPy 2.0.2, PyTorch 2.11.0+cu128, CUDA 12.8, and an available GPU. It verifies these in place and does not install or replace CUDA PyTorch. A mismatch stops before any run.

For a code-only release, commit and push the tested package to GitHub, then change only `PINNED_GIT_COMMIT` in the same stable Drive notebook to the verified full commit SHA. Run A–D to verify the selected release and storage identity before using the disabled continuation switch. Never upload or switch to an untested working-tree checkout. Keep datasets, checkpoints, results, secrets, and caches out of Git.

Cell B retrieves the canonical preflight JSON, its effective schedule CSV, and matching manifest using the verified main-account Drive API adapter. It stages these files locally by immutable Drive file-ID/version bundle; stale absolute paths embedded in historical preflight JSON are treated as filenames only and resolved beneath the canonical `revision_R1/results/preflight/schedules` folder. The original Drive files are read-only and are not regenerated or overwritten. `DRIVE_PATHS["preflight_drive_path"]` is the logical Drive path; `DRIVE_PATHS["preflight_staging_root"]` is local staging. Cells A–C require no DriveFS mount. Cell B also stages the existing v6.2 reference used by Cell C, preserving its original logical address under `v62_recovery_report_drive_path`.

Dataset sources are the existing configured Drive folders, resolved through the same main-account OAuth API. Cell B first verifies a matching local mmap cache; otherwise it reuses a hash-verified staged NPZ or downloads that exact existing Drive file once, verifying the preflight SHA-256 and frozen MD5. `DATA_ROOTS` and the two dataset roots in `DRIVE_PATHS` point at local API staging; `dataset_drive_roots` preserves the logical source addresses for safe reruns. Cell B inspects only archive headers. The runner builds or reuses its streamed mmap cache when each dataset is first needed, so setup does not decompress all arrays before training. No preflight, schedule, dataset, result, or checkpoint is regenerated by Cell B. External dataset downloads remain disabled.

The default OAuth v2/v3 builders give each requesting thread its own `httplib2.Http` transport with a 60-second socket timeout. Main-thread progress uploads cannot share an HTTP connection with lease heartbeats. Lease acquire/heartbeat/release operations are serialized per lease. If a CAS heartbeat succeeded remotely but its read-back failed, cleanup accepts a new ETag only when the remote owner and entire document exactly match that lease object's retained pending write. An unexplained ETag or owner change still rejects release. Cleanup and failure-reporting errors are attached to the primary exception rather than replacing it.

For a failed attempt whose matrix release also failed, run the separate `Recover_Matrix_Lease.py` cell after A–D in the original idle runtime. `recover_failed_matrix_lease` verifies the canonical FAILED record, frozen identities, attempt PID/timing, released run lease, stopped heartbeat threads, original runtime, exact diagnostic owner record and expiry. It publishes a recovery audit before CAS-releasing only the expired matrix record. It does not delete a lease, change any checkpoint/result, or launch training. A live or changed record is preserved. Rerun D after recovery, then explicitly enable F. Keep Run 1 finalized and skipped.
